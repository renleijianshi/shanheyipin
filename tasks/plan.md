# Implementation Plan: 库存与售后闭环

## Overview

按 M23 → M24 → M30 → M31 → M32 顺序建立库存审计与售后处理闭环；真实微信/支付宝退款保持关闭。

## Architecture Decisions

- M23 仅补齐余额所必需的最小仓库与批次引用，不实现 M17-M22 业务流程。
- 库存余额是查询缓存，任何变动必须与 M24 流水在同一事务中完成。
- 退款单与售后单分离；Provider 默认 Disabled，测试使用 Mock。
- 补发单独立建模，库存扣减使用来源单据幂等键并记录成本。

## Task List

1. M23/M24：库存余额、守恒校验、幂等流水和 Prisma 事务仓储。
2. M30：售后申请、商品明细、状态日志与归属/审核约束。
3. M31：退款单、累计金额保护、Mock/Disabled Provider 与回调幂等契约。
4. M32：补发单、地址快照、补发商品、成本和库存出库关联。
5. 全量验证、代码审查、长期状态更新并合并本地 main。

## Risks and Mitigations

- 并发超扣：余额行锁 + 乐观版本 + 数据库事务。
- 重复回调/操作：唯一幂等键 + 请求哈希。
- 真实资金误操作：真实 Provider 不实现，Disabled 默认失败关闭。
- 缺少上游批次数据：只提供最小主键骨架，正式入库由 M17-M22 后续接入。
