## 5. 技术实现方式

### 5.1 保留现有工程和 V19

沿用 uni-app/Vue 3 + Web Vue 后台 + TypeScript 模块化单体 + Prisma/MySQL；保留已确认的 V19 视觉与交互。
当前实际 API 入口是 Node `http`，不是完整 NestJS 应用。先复用现有 service/repository，将 HTTP 按领域拆分和装配，避免为换框架重写业务。
所有客户端通过同一 API 和数据库获得业务事实；本地 storage 只承担可丢弃缓存/草稿，不作为商品、订单或库存的权威来源。

### 5.2 公共客户端与服务端边界

- 小程序建立统一请求层：API 地址、会话、超时、业务错误、登录过期、加载/空/失败状态；用现有 Port 适配，逐页替换演示 store。
- 管理端使用独立会话与 RBAC，每个读写接口服务端鉴权，增加操作审计；菜单隐藏不能代替鉴权。
- 为消费者登录、地址、购物车、结算、订单、物流、售后与内容补 HTTP 路由；现有 catalog 路由继续复用。
- 媒体持久化对象键，展示层解析允许的 OSS 域名；运营上传走受权限保护的流程。
- API 金额为整数分；下单重新核价；数据库事务和唯一约束处理幂等与竞争。

### 5.3 交易与供应链

在同一事务上下文装配订单、库存预占及流水；不能在创建订单后单独调用库存服务并忽略失败。
明确订单取消与支付成功竞争、部分发货、超时任务重试、退款未知结果及补发失败的恢复机制。
先补仓库/批次可管理能力，再接质检入库、领料加工、成品批次和销售出库；复用既有金额/库存规则。
支付继续 Mock/Disabled，真实微信支付、真实退款与真实发货同步遵守 Deferred。全系统可先验收，但正式交易上线需单独完成真实渠道验收；本轮不索取商户资料。
