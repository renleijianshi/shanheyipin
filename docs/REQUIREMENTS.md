# REQUIREMENTS

## 当前有效范围

- 微信小程序、Web 管理后台、API、MySQL/Redis、对象存储、供应链/库存、会员营销、内容溯源和企业团购。
- 按 `tasks/M01` 至 `M46` 增量交付，每个模块独立分支、测试、Review、PR。

## 业务硬规则

- 金额统一使用整数分；服务端计算订单金额。
- SPU、SKU、库存批次分别建模；订单保存商品快照。
- 商品分类使用稳定唯一代码和父子树；小程序只展示启用分类，禁用父分类隐藏其整个子树。
- SPU 主数据独立于 SKU；SPU 媒体只保存 OSS 对象键，草稿默认不可见，上架前必须归属启用分类并至少有一张图片。
- SKU 独立于 SPU 和库存批次；价格只用整数分、重量只用整数克，SKU 编码全局唯一，可选条码全局唯一。
- 同一 SPU 的规格组合不得重复；规格名称和值按数据库校对规则做 Unicode 与大小写规范化、排序后，以稳定 SHA-256 签名建立数据库唯一约束。
- SKU 上架要求所属 SPU 已上架；M09 只建立 `BATCH` 库存模式标记，不创建或修改任何库存余额。
- 消费者商品列表、搜索和详情只返回启用分类链下的上架 SPU，并且至少包含一个上架 SKU；外部只使用稳定公开 UUID。
- 商品搜索关键词最多 50 字，公开列表每页最多 50 条；商品媒体继续只返回 OSS 对象键，不拼接或接受外部 URL。
- 每个用户只有一个购物车；同一 SKU 合并为一行，每行数量为 1-99，最多 100 种商品。
- 加购时必须重新校验 SKU、SPU 与完整分类祖先链可售状态；购物车不预占库存，失效商品保留展示但不计入有效件数和小计。
- 结算预览只接受当前用户拥有的地址与购物车条目，商品金额必须取服务端当前价；优惠暂为零金额明细占位，运费通过可配置报价器计算。
- 结算预览不锁库存且不是最终报价；创建订单时必须重新校验商品、价格和运费，M23 接入后同时原子校验并预占库存。
- 下单要求客户端提供 8-128 字符幂等键；以 `(user_id, idempotency_key)` 唯一约束和请求哈希保证重试回放，相同键不同请求必须拒绝。
- 订单必须保存商品、规格、图片、价格、地址、金额明细和初始状态日志快照；创建事务内再次校验地址、购物车、SKU/SPU/分类状态和价格，并清理已下单购物车条目。
- M13 尚无库存表，不得声称订单已锁库存；M23 必须把库存原子预占和取消释放接入订单事务/一致性流程，之后才能开放真实下单。
- 库存由余额、流水、批次共同构成；取消/超时释放锁定库存。
- 包装必须使用 BOM、加工任务、领料、损耗和成品批次。
- 售后区分仅退款、退货退款、补发、赔付；退货质检后才决定库存去向。
- 预售与现货库存隔离；关键后台操作保留审计记录。

## 支付阶段要求

- Real WeChat Pay = Deferred。
- Real Alipay = Deferred。
- 不索取任何微信/支付宝商户密钥、证书或商户资料。
- 先实现 `PaymentProvider`、`PaymentOrder`、状态机、幂等、回调接口、配置占位、`MockPaymentProvider`、`DisabledPaymentProvider`、单元测试和集成测试。
- 不做真实支付、真实退款、正式商户回调联调。
- 使用 Mock/Disabled Provider 跑通订单、库存、售后链路。
- 支付意图必须先持久化再调用 Provider；同一用户幂等键绑定订单与 Provider 请求哈希，并由数据库唯一约束处理并发竞争。
- Provider 超时或不确定异常记为 `UNKNOWN`，禁止盲目重试；Disabled 明确失败，Mock 只返回本地确认动作，不使用或模拟任何真实商户密钥。
- 支付回调必须先验签和严格解析，再在单个事务内核对支付单、Provider、平台交易号、金额与订单状态；回调事件和平台交易号均使用数据库唯一约束去重。
- 当前仅有 HMAC Mock 回调验证器；真实微信验签与解密仍为 Deferred，未配置真实验证器时不得开放微信回调入口。
